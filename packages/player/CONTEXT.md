# Player Context

The playback engine. Plays a single audio Segment at a time, exposes system controls (lock screen, notification bar, headphone buttons, audio ducking), and reports playback events. The Player is a pure executor — it has no opinion about what plays next, and no concept of a queue or list.

## Language

**Programme**:
A batch of Segments pre-generated by the Host for a given Channel. The Player works through a Programme sequentially. When a Programme is nearly exhausted — or an Intervention occurs — the Host generates a new Programme to replace it.
_Avoid_: queue, playlist, tracklist, set

**Segment**:
A single playable audio unit in a Programme. Either a Track (music) or an Interlude (TTS speech). The Player treats all Segments uniformly — it does not distinguish music from speech.
_Avoid_: item, entry, audio, track (when meaning the slot in a Programme)

**Now Playing**:
The Segment currently being played. Includes metadata surfaced to the OS (title, artist, artwork) for lock screen and notification display.
_Avoid_: current track, active track

**Lookahead**:
The next Segment, pre-loaded while Now Playing is still running. An internal implementation detail — not a domain concept visible to the user or the Host. Exists solely to ensure gapless playback between Segments.
_Avoid_: next track, buffer, prefetch (in domain discussions)

**Playback State**:
The real-time state of the player: position (seconds), volume, playback rate, and play/pause status.
_Avoid_: player state (too broad)

**Intervention**:
A user-initiated signal that causes the Host to discard the current Programme and generate a new one. Examples: a Track Request ("点歌"), a mood change, a voice or text instruction. The Player itself does not handle Interventions — it receives a new Programme from the Host.
_Avoid_: user input, command, request (when meaning the event that triggers regeneration)

**Audio Ducking**:
Automatic volume reduction of music Segments when another app (e.g. navigation, phone call) requests audio focus. Restored when focus is returned.
_Avoid_: volume fade, audio focus

## Relationships

- A **Programme** contains an ordered sequence of **Segments**
- Exactly one **Segment** is the **Now Playing** at any time
- The **Lookahead** is the next **Segment** in the current **Programme**
- An **Intervention** causes the **Host** (Radio context) to produce a replacement **Programme**

## Example dialogue

> **Dev:** "When the user taps 'play this song next', do we insert it into the Programme?"
> **Domain expert:** "No — that's an Intervention. The Player tells the Host. The Host generates a new Programme that starts with (or soon includes) that Track. The Player doesn't mutate Programmes."

> **Dev:** "Does the Player know it's playing an Interlude vs a Track?"
> **Domain expert:** "No. It has a URL and metadata. It plays it. That's all."

## Dual Playback Modes

The Player supports two coexisting modes (see ADR 0006):

- **Radio mode**: consumes a Programme (Segment[]) from the Host. No user queue manipulation. The concepts above (Programme, Segment, Lookahead, Intervention) apply.
- **Classic mode**: consumes a queue (Track[]) with full user control (add, insert next, remove, shuffle, play mode). The traditional playback model, preserved as-is.

A `playbackMode: 'radio' | 'classic'` discriminator determines which is active. Only one mode plays at a time. Mode switching is implicit: `loadProgramme()` enters radio mode; `playTrack()`/`playQueue()` enters classic mode.

## Flagged ambiguities

- "Queue" in Classic mode is user-visible and user-managed. "Programme" in Radio mode is Host-generated and opaque. These are distinct concepts that coexist — not a rename.
- The Player Controller layer treats both uniformly as "an ordered list of audio items to play". The mode distinction lives at the store level.
